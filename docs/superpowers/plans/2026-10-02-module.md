# Single jitpp Module Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan inline.

**Goal:** Build and exercise the concrete interpreter through `import jitpp;`.

**Architecture:** One module interface includes the global-owned class in its global module fragment and exports it with namespace using-declarations, matching native.isa. Ordinary C++ implementation files and assembly retain their symbols. CMake supplies the C++26 module dependency graph; Autotools remains usable for the header build.

**Tech Stack:** Linux x86-64, Clang, C++26, CMake 3.30+, Ninja, existing glog/gflags/udis86 dependencies.

**Spec:** User instructions in this conversation: one concrete interpreter, assembly references in the global module fragment, one jitpp module.

## Constraints and review focus

- Export interpreter and application from one provider, with no inheritance or PIMPL.
- Module consumers must run the same native/interpreted/native round-trip checks.
- Module builds must not depend on an Autotools-generated source-tree config header.
- Keep exceptions enabled: unsupported instructions use exception fallback.
- Verify Debug and Release and an external add_subdirectory consumer.
